# Аутентификация и изоляция тенантов (Stage 4)

## Модель доступа
- Аккаунты создаёт **администратор платформы** (`users.is_platform_admin`); публичной регистрации нет.
- Пользователь состоит в организациях через `memberships` с ролью `admin | member | viewer`.
  Роли org-уровня пока только разграничивают доступ к будущим ресурсам; управление пользователями и организациями — у администратора платформы.
- Первый администратор: `docker compose exec backend python -m app.cli create-admin --email you@example.com` (пароль запросит терминал, не печатается).

## Сессии и CSRF
- Вход: `POST /api/v1/auth/login` → cookie `wc_session` (**httpOnly**, `SameSite=Lax`, `Secure` в production). В БД хранится только SHA-256 токена.
- Срок: абсолютный `SESSION_TTL_HOURS` (168 ч) и простой `SESSION_IDLE_HOURS` (12 ч). Отключение пользователя или смена пароля отзывает все его сессии.
- CSRF: токен сессии отдаётся в ответе `login`/`me`; все `POST/PUT/PATCH/DELETE` обязаны присылать его в заголовке `X-CSRF-Token`.
- Пароли: Argon2id, минимум 12 символов. Неверный email и неверный пароль неразличимы (ответ и время).
- Защита от перебора: 5 неудач за 15 минут на IP или email → 429. Счётчик в памяти одного процесса; при нескольких воркерах перенести в БД.

## Изоляция организаций (два рубежа)
1. **Приложение:** зависимость `org_context` пускает в `/orgs/{org_id}/...` только участников; чужая организация → **404** (существование не раскрывается). Репозитории принимают `org_id` обязательным аргументом.
2. **PostgreSQL RLS:** на `memberships` включены `ENABLE` + `FORCE ROW LEVEL SECURITY`. Приложение работает под ролью `APP_DB_USER` (не суперпользователь, `NOBYPASSRLS`), в начале запроса задаёт `app.current_user`, `app.current_org`, `app.is_platform_admin`. Запрос без WHERE по организации всё равно не видит чужих строк.
   Миграции идут под владельцем схемы (`MIGRATION_DATABASE_URL`).
- **Правило для новых таблиц с данными организации:** колонка `organization_id NOT NULL`, индекс `(organization_id, …)`, `ENABLE`+`FORCE RLS` и политика по `app.current_org` — в той же миграции; в тест изоляции добавляется кейс на новую таблицу.

## Аудит
`audit_events`: вход, неудачный вход, выход, создание пользователей и организаций, смена пароля/статуса, добавление в организацию. Пароли и токены в журнал не попадают (тест).

## Тесты
```bash
cd backend
TEST_DATABASE_URL='postgresql+asyncpg://postgres@localhost:5432/postgres' pytest
```
URL — суперпользователь с правом создавать БД; на каждый запуск создаётся временная БД, миграции применяются настоящим `alembic`. Без `TEST_DATABASE_URL` DB-тесты пропускаются.
