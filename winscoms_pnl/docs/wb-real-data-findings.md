## 2. Как устроены деньги в строке «Продажа» (главная находка)
```
retailPrice            = retailPriceWithDisc          цена продажи (скидок продавца в отчёте нет)
retailAmount           = retailPrice × (1 − spp/100)  цена, оплаченная покупателем после СПП (округлена до ₽)
компенсация СПП (WB)   = retailPrice − retailAmount
номинальная комиссия   = retailPrice × commissionPercent / 100
vw + vwNds + ppvzReward = номинальная комиссия − компенсация СПП       ← может быть отрицательной!
acquiringFee           = retailPrice × acquiringPercent / 100
forPay = retailAmount − acquiringFee − (vw + vwNds) − ppvzReward
       = retailPrice − номинальная комиссия − acquiringFee
vwNds                  = 22% от vw (НДС на комиссию)
ppvzSalesCommission    — в формулу forPay не входит; смысл не установлен (не суммировать!)
```
Итоги по 87 продажам: выручка (`retailPrice`) **171 774** · номинальная комиссия **58 880,62 (34,3%)** · эквайринг **4 157,21** · `forPay` **108 736,31**.
При этом `vw + vwNds` в сумме **−6 957,98**, а с `ppvzReward` (2 511,48) — **−4 446,50**: «комиссия по полям `vw`» в этом периоде выглядит как **доход**, потому что в ней уже зачтена компенсация СПП 63 327 ₽.

**Следствия для P&L**
1. Брать комиссию как `Σ(vw + vwNds)` (п. 4.1 присланной разбивки) **нельзя** — расход комиссии занижается на сумму СПП и может стать отрицательным. Корректный расход «комиссия WB» = `vw + vwNds + ppvzReward + (retailPrice − retailAmount)`, что равно `retailPrice × commissionPercent / 100`.
2. Выручка по выбранной вами мере (`retailPriceWithDisc` = `retailPrice`) согласуется с `forPay`; `retailAmount` — не выручка продавца, а цена покупателя после СПП.
3. Компенсация СПП отдельной статьёй дохода **не показывается** — она учтена, если комиссия берётся номинальной (иначе была бы двойная).
4. `ppvzSalesCommission` исключён из расчётов до выяснения смысла (в выборке он ≠ ни `vw`, ни номинальной комиссии).
5. Эквайринг считается от `retailPrice`, не от `retailAmount`.

## 3. Строки «Возмещение издержек…» — неясное направление
По каждой из 348 строк `vw + vwNds + rebillLogisticCost = 0`, `forPay = 0`, `quantity = 2`. Это либо доход продавца (кредит через `vw`), либо расход, компенсируемый кредитом, — **по данным однозначно не определить**. Варианты итога к выплате за 01–11.07 (все остальные статьи уже учтены: `forPay` − логистика − хранение − приёмка − реклама = **87 256,42**):
- A: возмещение нулевое по эффекту — **87 256,42**
- B: кредит через `vw`/`vwNds` (+1 006,69) — **88 263,11**
- C: только расход `rebillLogisticCost` (−1 006,61) — **86 249,81**

**Нужно от вас:** сумма «К перечислению / Итого к оплате» за 01–11.07.2026 из кабинета WB (или платёжные документы). Она сразу покажет верный вариант и подтвердит остальную арифметику.

## 4. Технические выводы
- **Идентификаторы больше 2^53** (`reportId` ≈ 2.5·10¹⁶): Excel и JavaScript портят их (в выгрузке `reportId` уже округлён). Наш бэкенд хранит `int`/`bigint` без потерь; во фронтенд такие поля отдавать **строкой**.
- Типы в выгрузке смешанные (`vendorCode`, `sku`, `srid` — числа и строки); в БД артикулы/штрихкоды хранить **текстом**. В колонке `deliveryService` у строк без логистики Excel подставил даты — это артефакт выгрузки, не API.
- В Excel деньги — числа; в присланном JSON-примере — строки. Что вернёт реальный API, узнаем на первом запросе; нормализация принимает оба вида и всегда переводит в `Decimal(str(значение))`.
- `rrDate` и `saleDt` совпадают в 99,7% строк (различаются у 2 строк логистики). Период P&L предлагается считать по `rrDate` (дата строки отчёта).
- Колонки, пустые во всех 592 строках (`ppvzSupplierName`, `ppvzSupplierInn`, `declarationNumber`, `buyerTaxRegistrationReasonCode`, `utdUcdNumber/Date` и др.), в модель не выносим, сырьё сохраняется в `raw_records`.
