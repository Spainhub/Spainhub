# Интеграция с Wildberries (Stage 5)

Источник: `POST https://finance-api.wildberries.ru/api/finance/v1/sales-reports/detailed`, заголовок `Authorization: <токен>`.

## Что подтверждено, а что нет
| Что | Статус |
|---|---|
| Endpoint, заголовок, параметры `dateFrom`, `dateTo`, `limit` (≤100000), `rrdId`, `period` | со слов заказчика |
| Пагинация: первый `rrdId=0`, далее `rrdId` последней записи, конец — HTTP 204 | со слов заказчика; реализовано |
| Формат `dateFrom`/`dateTo` в запросе (сейчас `YYYY-MM-DD`) | **не подтверждено** — официальная документация недоступна из среды разработки |
| Допустимые значения `period` (сейчас `daily`, настройка `WB_REPORT_PERIOD`) | **не подтверждено** |
| Тело ответа — JSON-массив объектов | по присланному примеру |
| Смысл HTTP 402 | **не подтверждено**; сейчас останавливаем задание с пояснением |
| Уникальность `rrdId` внутри аккаунта | **не подтверждено**; ключ дедупликации `(аккаунт, endpoint, rrdId)` |
| Лимит 1 запрос/мин для персонального токена | со слов заказчика; интервал `WB_MIN_INTERVAL_SECONDS=65` |

Все места, зависящие от неподтверждённого, собраны в `integrations/wildberries/client.py` (`build_body`, `_parse`). Первый реальный запрос покажет расхождения: ошибка 400 будет видна в интерфейсе заданий и в `sync_jobs.error_message`.

## Как работает синхронизация
1. Администратор организации создаёт аккаунт (`POST /orgs/{org}/seller-accounts`), токен шифруется Fernet и больше не возвращается (только последние 4 символа).
2. `POST …/validate` — проверка одним запросом (расходует лимит API, поэтому повтор раньше интервала → 429).
3. `POST …/sync` создаёт задание: период — с 1-го числа месяца `HISTORY_MONTHS` назад по сегодня **по Москве**. Одновременно у аккаунта может быть только одно активное задание (уникальный индекс в БД).
4. Воркер (`python -m app.jobs.worker`, отдельный сервис Compose) делает **один HTTP-запрос за шаг**. Между шагами курсор `rrdId`, счётчики и время следующего запроса лежат в БД, поэтому перезапуск на любом этапе безопасен.
5. Страница сохраняется в `raw_records` (JSONB, без потерь) через `INSERT … ON CONFLICT DO NOTHING`: повторная обработка не создаёт дублей. Конец данных — только HTTP 204, а не «страница меньше лимита».
6. Ошибки: 401/403 → задание остановлено, аккаунт `auth_error` (нужен новый токен: `PUT …/token`); 400/402 и ошибки разбора → остановка с понятным сообщением; 429 → пауза по `Retry-After` (или `X-Ratelimit-Retry`) с экспоненциальным ростом, до 10 попыток; 5xx/сеть/таймаут → до 5 попыток с задержкой 1, 2, 4… мин (не меньше интервала лимита). После исчерпания: `failed`, а если часть страниц уже сохранена — `partial`. Ручной повтор (`POST …/sync-jobs/{id}/retry`) продолжает с сохранённого курсора.
7. Период помечается успешным (`succeeded`, `accounts.last_sync_at`) только после HTTP 204.

Статусы задания: `queued` · `running` · `succeeded` · `failed` · `partial` · `cancelled`.

## Наблюдения по присланному примеру ответа
- **Пример синтетический**, не реальные данные: в одной строке «Продажа» одновременно `penalty=231.35`, `paidStorage=12647.29`, `deduction=6354`, `paidAcceptance=865`, а `rrDate=2025-10-20` раньше периода отчёта (март 2026). Реальные строки так не выглядят, поэтому **знаки, смысл полей и вхождение одних сумм в другие нужно подтверждать на реальных данных**, а не по этому образцу.
- **Деньги приходят строками** (`"retailPriceWithDisc": "399.68"`) → везде `Decimal`/`NUMERIC`, никакого float.
- В примере поле называется **`retailPriceWithDisc`** (не `...Rub`, как мы писали ранее). Для формулы выручки используем имя поля из реального ответа; подтвердить.
- В примере `currency: "BYN"`, а не RUB. Суммы в разных валютах **не складываются** без явной конвертации: в P&L агрегаты считаются по паре (аккаунт, валюта).
- Типы операций приходят на русском (`docTypeName: "Продажа"`, `sellerOperName`), а не «Sale/Return» — маппинг будет по реальным значениям; неизвестные типы попадают в отчёт как «не классифицировано», а не молча в ноль.
- В записи есть персональные и коммерческие данные (`kiz`, ИНН, адреса). `raw_records.payload` хранится как есть, но не показывается в интерфейсе без необходимости и не логируется.

## Что делать с присланной разбивкой P&L (черновик для Stage 7)
Принята как **черновик к обсуждению**, не как утверждённые формулы. Из того, что нужно решить до реализации движка:
1. **Выручка**: ранее выбран `retailPriceWithDisc`, а в разбивке стоят `retailPrice × quantity` (п. 1.1) и `retailAmount` (п. 14, 4.2); по документации, на которую ссылается текст, `retailPrice = retailPriceWithDisc`, но в примере `1249` против `399.68`. Нужна одна меру выручки.
2. **Двойной учёт** в разбивке: `deduction` входит в п. 5.8, 5.10 и в рекламу (7.1); `rebillLogisticCost` — в п. 5.4 и 5.10; `penalty` — в 5.7 и 5.11; `acquiringFee` — отдельно и в «прочих расходах». Каждое поле должно попадать ровно в одну строку.
3. **НДС**: нет подтверждённой ставки; в разбивке п. 1.2 и 14 требуют ставку по товару (справочник товаров), а `vwNds` — НДС только с комиссии. Нужны настройка политики организации и справочник ставок.
4. **Знаки** (`additionalPayment`, возвраты, `deduction`) и отнесение `bonusTypeName` к статьям — по реальным данным и таблице значений.
5. **Реклама** внутри `deduction` выделяется по `bonusTypeName`; нужен список реальных значений.
6. Строки 8–13 (OPEX, амортизация, налоги, НДС-регистр) — ручной ввод/импорт; не вычисляются из отчёта WB.
