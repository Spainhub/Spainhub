# P&L Report Wildberries — Google Sheets + Apps Script

Все скрипты лежат в папке [`apps-script/`](apps-script). Каждый файл вставляется в редактор Apps Script **целиком** под тем же именем
(файл `Index.html` — как HTML-файл `Index`).

| Файл | Статус | Что делает |
|---|---|---|
| `Code.gs` | **заменить** | Загрузчик WB (переписан: очередь, продолжение по таймауту, перекрытие дней, журнал), меню, Calculation, Web App |
| `Index.html` | **заменить** | Web App: вкладки «P&L по периодам» / «P&L по SKU», графики при наведении, плашка статуса данных |
| `Calculation_sku.gs` | **новый** | Лист `Calculation_sku` + данные для вкладки SKU, лист себестоимости `Cost_sku` |
| `Charts.gs` | **новый** | Дневные ряды для графиков при наведении |
| `Data_check.gs` | **новый** | Контроль пропусков: лист `Data_check`, письмо при проблемах, авто-дозагрузка |
| `Auth.gs`, `Report_finans_*.gs`, `Get_sku_*.gs` | без изменений | — |

## Установка (5 минут)

1. Apps Script → замените содержимое `Code.gs` и `Index.html`, добавьте файлы `Calculation_sku.gs`, `Charts.gs`, `Data_check.gs`. Сохраните.
2. **Настройки проекта → Часовой пояс: `(GMT+03:00) Москва`**. Такой же пояс — у самой таблицы (Файл → Настройки).
3. Обновите страницу таблицы → меню «Отчёты МП» → **«Контроль данных» → «Установить ежедневный триггер»**.
   Делать это нужно из-под того пользователя, чей токен WB сохранён (триггер работает от его имени и берёт его токен).
   Старые триггеры `loadYesterday` / `cleanupOldRows` удаляются автоматически.
4. Если данных меньше 3 месяцев — «Wildberries — P&L» → «Первый запуск (3 месяца)». Скрипт сам продолжит, если не уложится в 6 минут.
5. Заполните себестоимость за единицу в листе **`Cost_sku`** (список SKU появится сам после первого пересчёта).
6. Развернуть → **Управление развёртываниями → Изменить → Новая версия** (иначе Web App покажет старый `Index.html`).
7. «Контроль данных» → «Проверить пропуски» — посмотрите лист `Data_check`.

## 1. График строки при наведении

- Наведите мышь на любую строку таблицы — над строкой появляется карточка с графиком (по горизонтали — у курсора; если сверху нет места — под строкой).
- **Строки, которые считаются из Data_wb** (выручка, возвраты, к перечислению, СПП, расходы МП, комиссия, логистика, хранение, штрафы, доли в %):
  дневной ряд **за весь период отчёта** + пунктир «среднее за 7 дней». Сверху — итог за период, среднее в день, динамика «последние 7 дней к предыдущим 7» (▲/▼; рост расходов подсвечивается как негатив).
- **Наведение на ячейку дня** подсвечивает этот день на графике (вертикальная линия + значение), **на ячейку месяца** — подсвечивает месяц и показывает его сумму.
- **Строки с ручным вводом** (COGS, OPEX) и зависящие от них (ВП, чистая прибыль) по дням посчитать нельзя — для них два мини-графика по колонкам отчёта: «Месяцы» и «Дни» (у каждого своя шкала, чтобы дни не терялись на фоне месяцев).
- Во вкладке SKU — выручка SKU по неделям (светлый столбец — неполная неделя), ВП, маржа, ABC/XYZ.
- Переключатель «Графики при наведении» справа от вкладок (запоминается в браузере). `Esc` или прокрутка — скрыть.
- Дневные ряды грузятся фоном после таблицы (`PnlChart_getDailySeries`) и кэшируются на 6 часов до изменения данных/периода — таблица не замедляется.

## 2. Лист `Calculation_sku` и вкладка «P&L по SKU»

- Лист создаётся автоматически справа от `Calculation`. **Шапка (строки 1–5) — ссылки на шапку `Calculation`**, т.е. та же; период задаётся там же (или фильтром Web App).
- Таблица с `A6`: `№ | SKU | Категория товара | Выручка | Логистика | % | Расходы | Себестоимость | ВП (MG) | Маржа, % | Доля, % | XYZ | ABC`.
- **Логика полей — как в `Calculation`** (те же колонки Data_wb и те же условия SUMIFS, только с разбивкой по `nmId`):

| Поле | Формула | Строка Calculation |
|---|---|---|
| Выручка | Σ V («Продажа») − Σ V («Возвраты») | 009 |
| Логистика | Σ AH («Логистика») | в т.ч. логистика |
| % | Логистика / Выручка | в т.ч. логистика, % |
| Расходы | (Выручка − К перечислению) + Логистика + Хранение (BL) + Штрафы (BI+BM) | 025 |
| Себестоимость | себестоимость ед. из `Cost_sku` × (продано − возвращено), шт. | 020 |
| ВП (MG) | Выручка + доход СПП − Себестоимость − Расходы | 030 |
| Маржа, % | ВП / (Выручка + доход СПП) | 035 |
| Доля, % | Выручка SKU / Выручка итого | колонка «Доля» |
| ABC | по выручке: A — до 80% накопленной, B — до 95%, C — остальное | — |
| XYZ | коэффициент вариации недельных продаж, шт.: X ≤ 10%, Y ≤ 25%, Z > 25%; «—» если < 4 полных недель | — |

- Строки без `nmId` (обычно хранение, штрафы, удержания) — отдельной строкой **«Без SKU (общие начисления)»**, чтобы «Итого» сходилось с Data_wb.
- Себестоимость: WB API её не отдаёт, в `Calculation` она вводится вручную суммой. Для SKU нужна цена за единицу — лист **`Cost_sku`**
  (новые SKU дописываются сами, введённые значения не затираются). SKU без себестоимости подсвечены.
- Пересчёт: автоматически после ежедневной загрузки, при открытии вкладки в Web App (если изменились данные/период/себестоимость — иначе из кэша), из меню «Пересчитать P&L по SKU».
- Во вкладке: поиск по SKU/артикулу/категории, фильтр A/B/C, сортировка кликом по заголовку, экспорт PDF/Excel/печать текущей вкладки.
- Пороги ABC/XYZ и имена полей меняются константами в начале `Calculation_sku.gs`.

## 3. Проверка на пропуски при автозагрузке

### Что было найдено в текущем коде

| # | Проблема | Чем грозило |
|---|---|---|
| 1 | Окно хранения `RETENTION_DAYS = 90` дней, а колонка M листа `Calculation` — **целый месяц 3 месяца назад** (30.09 → июнь) | Самый старый месяц почти пустой: 30.09 граница 02.07 → июнь = 0, июль без 1-го числа. **Главная «дыра» в отчёте** |
| 2 | Первый запуск грузил 30 дней (`FIRST_RUN_DAYS = 30`), а не 3 месяца | Месяцы K:M пустые до накопления |
| 3 | Ежедневно грузились только 2 дня (`today-2 … today`) | Один сбой триггера (429, 5xx, истёкший токен, WB опубликовал день позже) — и день потерян навсегда |
| 4 | По таймауту загрузка останавливалась с сообщением «Запустите ещё раз» | В триггере этого никто не видит — хвост периода не загружался |
| 5 | Строки писались только после загрузки всех страниц чанка | Принудительная остановка на 6-й минуте — потеря всего чанка |
| 6 | 5xx и сетевые исключения не повторялись | Падение всего запуска |
| 7 | Между чанками не было паузы 1 запрос/мин | Лишние 429 и трата времени |
| 8 | `new Date()` в часовом поясе проекта (у нового проекта — не Москва) | «Вчера» и граница очистки сдвигались на день |
| 9 | Очистка удаляла строки по одной (`deleteRow`) | На тысячах строк — таймаут, очистка не доходила до конца |
| 10 | Если в Data_wb только заголовок, новые поля API не дописывались в шапку | Данные сдвигались относительно заголовков → формулы по буквам (V, Z, AB…) читали не те колонки |
| 11 | Ручной запуск во время триггера | Две загрузки параллельно → дубликаты |
| 12 | Нет журнала и оповещений | О пропусках узнавали по «странным» цифрам |

### Что сделано

- **Окно хранения = с 1-го числа месяца 3 месяца назад** (МСК) — и для первого запуска, и для очистки. Все колонки `Calculation` всегда полные.
- **`dailyUpdate`** (ежедневный триггер): перезапрашивает последние **7 дней** (дубликаты отсекаются по `rrdId`), догоняет, если триггер не работал несколько дней, и **дозагружает пропуски** из более ранних дней (до 3 попыток на день).
- **Очередь загрузки** в ScriptProperties: запись после каждой страницы, курсор (дата + `rrdId`) сохраняется, при нехватке времени скрипт **сам продолжает через минуту**; при ошибке — повтор через 15 минут (до 3 раз); 401/402/403 — сразу в журнал.
- Повторы 429 (с учётом `X-Ratelimit-Retry`), 5xx и сетевых ошибок; лимит «1 запрос в минуту» соблюдается между всеми запросами, в том числе между запусками.
- Блокировки (`LockService`): параллельные загрузки исключены, задания из меню во время загрузки не теряются.
- Лист **`Load_log`** — журнал каждой загрузки (период, строк, статус, ошибка).
- Лист **`Data_check`** (после каждой загрузки и из меню):
  - пропущенные дни (нет ни одной строки за `rrDate`) и дни с «провалом» (строк < 30% медианы соседних дней);
  - дата последних данных и время последней успешной загрузки (тревога, если > 36 ч);
  - **структура**: колонки V, Z, AB, AH, AR, BI, BL, BM, на которые ссылаются формулы, не «уехали» (AB = `rrDate`, денежные — числовые поля; эталон запоминается при первой проверке);
  - типы операций в колонке Z: какие приходят и какие не попадают в формулы;
  - дубликаты `rrdId`, строки без даты, строки старше окна, наличие ежедневного триггера, «зависшая» очередь;
  - таблица по дням: дата, строк, продажи, статус.
- **Письмо** владельцу при ошибках (не чаще раза в день на одну и ту же проблему; адрес — `GAP_NOTIFY_EMAIL` в `Data_check.gs`).
- **Плашка в шапке Web App**: «✓ Данные полные · данные по 29.09.2026» или «⚠ пропущено дней: 2».

### На что обратить внимание (логику `Calculation` не менял)

1. **«Возвраты» vs «Возврат».** Формулы `Calculation` ищут в колонке Z значение `"Возвраты"`. В отчёте WB тип операции обычно называется «Возврат». Если так — возвраты не вычитаются из выручки.
   `Data_check` покажет реальные значения колонки Z и предупредит об этом. Исправление — заменить строку в `calcFormula()` (строка 10) и константу `SKUCALC_OPER_RETURN`, затем `forceRebuildCalculationSheet`.
2. **Покрытие периода.** Колонки `Calculation` = 6 последних дней + 3 предыдущих полных месяца. Дни текущего месяца до этих 6 дней (например, 01–24.09 при отчёте на 30.09) не попадают ни в одну колонку и в «Сумму».
   Вкладка SKU и дневные графики считают весь период из шапки (`G4 … E4`).
3. Колонки Data_wb в формулах заданы буквами. Если WB добавит новое поле, оно допишется в конец и буквы не сдвинутся; если всё же сдвинутся — `Data_check` сообщит об этом.
